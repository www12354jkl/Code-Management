## 关键数据流

1. **双 Token 认证、刷新轮换与注销防护**
   - `AuthServiceImpl` 签发 Access Token（默认 30 分钟，`type=access`）与 Refresh Token（默认 7 天，`type=refresh` + 唯一 `jti`）。
   - 主动调用 `POST /api/auth/logout` 时同时将传入的 Access Token 与 Refresh Token 写入 Redis `token:blacklist:{token}`（TTL 取剩余有效期）；忘记密码/重置密码时写入 `token:revoke-before:{userId}` 毫秒时间戳，使此前签发的所有旧令牌即时失效。
   - **双重校验关卡**：网关层 `GatewayAuthFilter`（Order `HIGHEST_PRECEDENCE + 10`）与下游微服务 `JwtAuthFilter` 均校验黑名单与 `token:revoke-before`，且严格拒绝将 `refresh` 令牌用作业务访问令牌；同时通过 `hasUnsafePathSyntax` / `isUnsafePath` 拦截 `;`、`..`、`\` 及 `%2e`/`%2f` 编码绕过。当 Redis 不可用时显式返回 HTTP `503`（Fail-closed），避免降级放行。
   - 前端 `request.ts` 在并发请求遇到 `401` 时通过共享 Promise `refreshing` 实现单飞（Single-flight）调用 `/api/auth/token/refresh`，刷新后重放原请求，服务端则同步将旧 Refresh Token 拉入黑名单完成轮换。

2. **WebSocket 一次性票据握手与动态发现**
   - 为避免长期有效的 Access Token 出现在 WebSocket URL 查询参数中被代理/日志泄露，客户端先携带 Bearer Token 请求 `POST /api/chat/ws-ticket`，`WsTicketService` 生成 32 位随机票据写入 Redis `ws:ticket:{ticket}`（TTL `30s`）。
   - 客户端发起 `WS /ws?ticket=...` 连接后，网关 `GatewayAuthFilter` 校验 Redis 中存在该票据并附加请求头 `X-Ws-Ticket`；随后由自定义路由过滤器 `WsLoadBalancerGatewayFilterFactory`（Order `RouteToRequestUrlFilter + 200`）从负载均衡器选中的 `easychat-chat-service` 实例元数据读取 `ws-port`（默认 `8083`），将目标 URI 重写为 `ws://{host}:{ws-port}/ws?ticket=...`。
   - 请求抵达 Netty Pipeline 后，`AuthWsHandler` 调用 `wsTicketService.consume(ticket)`（底层 Redis `GETDEL` 原子消费，确保仅用一次），绑定 `Channel` 的 `USER_ID` 属性并在 `WsSessionManager`（按 `userId` 划分 64 路分段锁串行切换连接，锁外关闭被顶替旧连接）与 `WsSessionRegistry`（`markOnline` / Lua CAS `refresh` / Lua CAS `markOffline`）中登记在线状态，随后交由 `WsOnlineStatusBroadcaster` 的 16 路按 `userId` 分片单线程条带池异步广播 `ONLINE_STATUS`（绑定应用类加载器、透传 `traceId`、保证同用户 FIFO 并隔离单好友推送异常）。

3. **单/多实例消息发送幂等、广播推送与限时撤回**
   - `POST /api/chat/message` 进入 `MessageServiceImpl.sendMessage`：校验会话与成员归属后，先按 `uk_message_sender_client_msg` 检查（`findByClientMsgId` + `DuplicateKeyException` 兜底）确保网络重传不会产生重复消息，随后原子推进 `conversation.last_message`。
   - 推送阶段经 `WsMessageSender -> WsPushRouter` 分发：
     - `easychat.ws.delivery=local`：`LocalWsPushRouter` 直接通过 `WsChannelWriter` 写入当前实例的 `Channel`。
     - `easychat.ws.delivery=kafka`：`KafkaWsPushRouter` 序列化 `WsPushEvent`（含 `toUserId`、`type`、`payloadJson`、`traceId`）发往 Kafka 主题 `easychat-ws-push`；每个 `easychat-chat` 实例通过 `WsDeliveryConfig` 动态生成独立消费组 `${spring.application.name}-ws-push-${wsInstanceId}` 实现全量广播消费，`WsPushKafkaConsumer` 仅在本地 `WsSessionManager` 存在活跃 `Channel` 时执行推送并继承 MDC `traceId`。
   - `POST /api/chat/message/{id}/recall` 允许发送者在 2 分钟窗口内撤回文本/图片/文件消息，将 `message.status` 置为 `2`、刷新会话摘要（若撤回的是最新消息则回退为 `[已撤回]`）并向全员广播 `MESSAGE_UPDATE`。

4. **Dubbo 跨库协调、503 降级与端到端链路追踪**
   - `easychat-chat` 通过 `@DubboReference(cluster = "failfast", retries = 0, mock = ...)` 消费 `UserQueryService`（`UserQueryServiceFallback` 在上游不可用时统一抛出 `503` `AppException` 并由 `GlobalExceptionHandler` 映射响应，避免关键发信/建群/单聊校验误报 `404`/`400`；列表头像昵称、撤回/邀请文案补全等非关键展示路径则由 `UserQuerySupport` 显式捕获 `503` 后优雅降级为空）；`easychat-user` 消费 `FriendRequestService`（好友申请实时弹窗提醒）与 `ConversationDeleteService`（删好友时同步清理单聊会话并通知双端 `CONVERSATION_REMOVED`）。
   - Dubbo 采用 `register-mode: interface` 与 `FORCE_INTERFACE`，避免应用级注册与 Spring Cloud Nacos HTTP 实例端口混淆。
   - HTTP 层 `TraceIdFilter` 读取/生成 `X-Request-Id` 写入 SLF4J MDC `traceId`，`TraceIdDubboFilter` 自动在 Provider 与 Consumer 间透传该 MDC 字段，Kafka `WsPushEvent` 同样携带并恢复 `traceId`。

## 外部依赖与服务

- **MySQL 8.4**（双库 `easychat_user`、`easychat_chat`）：由 Flyway 在服务启动时自动执行迁移（`easychat_chat` 已包含 `V1~V7`），详见 [[数据库设计]] 与 [[html/easychat-erd.html|E-R 图]]。
- **Redis 7.4**：统一支撑 JWT 黑名单/改密吊销线、WS 一次性票据、Netty 在线节点注册表、邮箱验证码与 `@RateLimit` 接口限流，详见 [[Redis与Kafka设计]]。
- **Kafka 3.9 / Redpanda v24.2**：在多实例水平扩展模式下承担跨实例 WS 事件广播总线（主题 `easychat-ws-push`），详见 [[Redis与Kafka设计]]。
- **Nacos 2.4.3 & Alibaba Sentinel**：承担微服务注册发现、Netty `ws-port` 元数据传递，以及 Gateway / User / Chat 三端流控规则本地基线与 Nacos 动态下发。
- **腾讯云 COS & QQ SMTP**：承载头像/群头像/聊天文件公开读存储与 HTML 邮件验证码发送。
